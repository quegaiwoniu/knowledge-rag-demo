# Day 4 AI 工作台重构与本机 JDK 稳定启动设计

## 1. 背景

当前项目已经完成了 Day 4 后端 `POST /ai/extract` 接口设计与实现，但如果只有后端接口，学习闭环还不完整：

- 无法在前端直接验证结构化抽取效果
- 无法演示真实业务页面里的输入、加载、失败、结果展示闭环
- 后端启动仍然容易受到终端默认 JDK 版本影响，稳定性不足

更重要的是，如果前端继续沿用“Step 1 / Step 2 / Step 3”的学习步骤页心智，后续做 Day 5 / Day 6 时，大概率还会再次重构首页。

因此这次设计不再采用“仅追加 Step 4”的补丁式思路，而是直接把首页升级成一个轻量、可扩展、可演进的 AI 工作台，同时把后端启动方式切成项目内固定的本机 JDK 启动方式。

## 2. 目标

本次设计覆盖两个子目标：

### 2.1 前端目标

把现有首页重构成一个轻量 AI 工作台，满足以下要求：

- 首页心智从“学习步骤页”升级为“AI 能力工作台”
- 至少承载 4 类能力卡片：AI 连通性、文本总结、结构化抽取、RAG 能力预留
- `/ai/extract` 作为本次重点能力，具备更完整的业务化展示
- 页面结构支持后续继续接入 classify、RAG 问答、检索、引用展示等能力
- 保持代码层面易拆分、易维护、易继续讲解

### 2.2 启动方式目标

把后端启动方式从“依赖当前终端碰巧使用哪个 Java”改成“项目脚本显式指定稳定 JDK”：

- 固定优先使用本机稳定 JDK 路径
- 启动逻辑对 PowerShell / cmd 更友好
- 降低新终端、新电脑、IDE 外部启动时的环境漂移问题
- 让项目接手者看到脚本就知道该如何启动

## 3. 范围

本次设计包括：

- 前端 AI 工作台首页重构
- 前端 `/ai/extract` 业务能力卡设计
- 前端 API 与类型定义扩展
- 前端页面状态、布局与结果展示设计
- 后端本机 JDK 启动脚本设计
- 文档落点与后续学习价值说明

本次设计不包括：

- 前端路由体系重构
- UI 组件库引入
- 后端部署脚本
- Docker 化
- API Key 配置托管改造

## 4. 方案选型

### 方案 A：单独新增一个前端页面 /extract

做法：

- 引入路由
- 单独创建结构化抽取页面
- 首页只保留导航入口

优点：

- 页面边界最清晰
- 后续功能变多时更容易扩展

缺点：

- 对当前学习项目来说偏重
- 会把 Day 4 的重点从“结构化抽取”分散到“前端页面架构”

### 方案 B：在现有首页中新增 Step 4 结构化抽取面板

做法：

- 保留现有首页结构
- 继续沿用 `Step 1 / Step 2 / Step 3` 的节奏，新增 `Step 4`
- API、类型、组件按现有方式扩展

优点：

- 最符合当前项目的演进方式
- 学习路径连续，适合课堂式/同事分享式演示
- 改动范围适中，收益高

缺点：

- `App.tsx` 会继续增长一些

### 方案 C：借这次机会把首页整体重构成 AI 工作台

做法：

- 重组现有 ping、summary、extract、rag 结构
- 把首页改成更强业务化的 AI 控制台

优点：

- 企业感最强
- 后续扩展性最好

缺点：

- 如果没有范围控制，容易把学习任务变成“大改前端架构”

### 推荐方案

采用 **方案 C：直接把首页升级为 AI 工作台，但控制在单页重构范围内**。

原因：

- 你已经明确后续要继续推进 Day 5 / Day 6
- 现在重构比未来反复返工更划算
- 更符合“可扩展性、高价值、可学习性”的目标
- 仍然可以控制边界：不引路由、不引组件库、不做无关重构

## 5. 前端设计

## 5.1 页面定位

首页不再强调“Step 1 / Step 2 / Step 3”，而是升级成一个轻量 AI 工作台。

推荐的工作台信息架构：

- 顶部：工作台标题 + 项目说明 + 后端健康状态
- 主体：能力卡片网格
- 卡片类型：
  - AI 连通性验证卡
  - 文本总结卡
  - 结构化抽取卡
  - RAG 能力预留卡

这样做的价值是：首页表达的不是“今天学到了第几步”，而是“这个项目目前具备哪些 AI 能力，以及每个能力如何演进”。

## 5.2 页面交互

结构化抽取卡应包含以下交互：

### 输入区

- 多行文本框
- 示例文本按钮
- 清空按钮
- 开始抽取按钮

### 执行区状态

- 提交中禁用按钮与输入框
- 展示“正在抽取结构化信息”的加载反馈

### 结果展示区

按真实业务后台常见阅读方式分块展示：

- 标题：单独高亮展示
- 分类：枚举标签展示
- 优先级：枚举标签展示，并通过颜色区分等级
- 关键词：标签组展示

### 异常反馈区

- 请求失败时展示清晰错误消息
- 保留后端返回的业务错误信息，方便学习接口边界

## 5.3 页面风格原则

这次不追求花哨视觉，而追求“真实企业内部工具”的感受：

- 信息层次清楚
- 字段与状态分区明确
- 结果展示便于阅读和截图
- 后续很容易继续接 classify / rag / search / citation 等能力

## 5.4 工作台级可扩展性设计

这次重构的重点，不只是把页面“改好看”，而是把首页组织方式调整成可持续演进的结构。

推荐的设计原则：

- 每个 AI 能力都对应一张职责清晰的卡片
- 卡片内部遵循统一模式：输入区 / 操作区 / 结果区 / 状态区
- 公共视觉语义尽量复用，例如标题、说明、状态提示、卡片容器
- 把“能力接入”与“页面骨架”分离，后续加新能力时只需新增卡片和 API 接线

这对学习的价值很高，因为它能让你和同事看到：

- 什么叫“可扩展的前端能力工作台”
- 什么叫“面向未来能力扩展做边界设计”
- 什么叫“不是每次新增能力都去堆首页”

## 5.5 类型设计

前端新增 `ExtractResponse` 类型，与后端契约保持一致：

```ts
export type ExtractResponse = {
  title: string;
  category: "BUG" | "FEATURE" | "QUESTION" | "COMPLAINT";
  priority: "LOW" | "MEDIUM" | "HIGH";
  keywords: string[];
};
```

设计原则：

- 字段名与后端保持一致
- 枚举值不做二次翻译，便于联调和排错
- 展示时可在组件层再做中文映射

## 5.6 API 调用设计

在 `aiApi.ts` 中新增统一调用函数：

```ts
extractText(text: string): Promise<ExtractResponse>
```

行为与 `summarizeText` 保持一致：

- `POST /ai/extract`
- 请求体为 `{ text }`
- 如果 `response.ok` 或 `payload.success` 不成立，则抛出前端可展示的错误

## 6. 后端本机 JDK 稳定启动设计

## 6.1 问题定义

当前后端虽然能运行，但启动成功依赖于当前终端环境中的 Java 版本。如果终端继承的是旧 JDK，就会出现：

- Maven 能启动但编译失败
- Spring Boot 无法正常运行
- 同样的命令在不同终端结果不一致

这类问题在企业项目里很常见，因此值得在学习项目里提前处理。

## 6.2 设计原则

后端启动脚本应满足：

- 显式指定稳定 JDK
- 本地开发优先
- 命令清晰、可直接复用
- 不把密钥写进脚本

## 6.3 方案选型

### 方案 A：只依赖系统环境变量 JAVA_HOME

优点：

- 最简单

缺点：

- 最容易漂移
- 不利于项目级知识沉淀

### 方案 B：在项目内提供启动脚本，脚本内显式切换 JDK

优点：

- 最稳定
- 最符合当前诉求
- 新电脑接手时成本更低

缺点：

- 需要维护一份脚本

### 推荐方案

采用 **方案 B：项目内固定启动脚本**。

## 6.4 启动脚本设计

建议在后端项目中提供本地启动脚本，例如：

- `knowledge-rag-demo/scripts/run-backend.ps1`
- `knowledge-rag-demo/scripts/run-backend.cmd`

脚本职责：

1. 定位稳定 JDK 路径
2. 显式设置本进程 `JAVA_HOME`
3. 把 JDK `bin` 放到当前进程 PATH 前面
4. 切换到后端项目目录
5. 执行 Maven 启动命令

目标命令保持现有项目习惯：

```powershell
mvn -s .mvn/settings.xml spring-boot:run
```

但要确保这个 `mvn` 是在稳定 JDK 环境下执行的。

## 6.5 路径策略

优先采用你当前机器上已经验证可用的稳定 JDK 路径。

实现时可采用以下思路：

- 优先读取脚本内配置路径
- 如果路径不存在，给出清晰错误提示
- 后续如果你更换 JDK，只需要改一处脚本

这比“把 JDK 版本要求写在 README 里，靠人记住”更贴近真实项目实践。

## 7. 文档设计

建议补充一份中文说明文档，至少包含：

- 前端 AI 工作台的定位
- 结构化抽取卡的用途
- 如何启动前后端
- 后端为何使用项目脚本固定 JDK
- API Key 不提交仓库的注意事项

文档仍放在你已经约定好的后端 `docs` 目录中，便于统一沉淀。

## 8. 测试与验收

本次完成后的验收标准：

### 前端

- 首页已从步骤页升级为 AI 工作台
- 页面可直接发起 `/ai/extract` 请求
- 能看到结构化结果展示
- 加载、失败、清空、示例填充都可正常工作
- AI 连通性、文本总结、结构化抽取、RAG 预留 4 张能力卡片语义统一
- 页面样式与当前项目整体一致，但可明显看出更强的企业业务感

### 后端启动

- 使用项目脚本可稳定在本机 JDK 下启动
- 不再依赖当前终端默认 Java 版本
- 不把 API Key 写入脚本或提交仓库

## 9. 学习价值

这次补充不是单纯“把前端补齐”，而是在补两个真实业务里很重要的意识：

1. AI 能力不是只有接口，还要有可演示、可联调、可观察的前端承接面
2. 本地开发稳定性也是工程能力的一部分，JDK 漂移问题要尽量项目内收敛

这两点都很适合拿来给同事讲，也很适合作为你后续继续做 Day 5 / Day 6 的基座。

## 10. 最终结论

Day 4 的下一步应当采用以下落地方式：

- 前端直接重构为轻量 AI 工作台
- `/ai/extract` 作为本次重点能力卡做完整业务化展示
- 后端新增项目级本机 JDK 固定启动脚本
- 文档继续统一沉淀到后端 `docs` 目录

这套方案更符合你现在的目标：可扩展性更强、学习价值更高、也更接近企业真实项目的演进路径。
